# MindosShop

一个纯净、轻量的原生 Windows 应用商店客户端。以联想应用商店与腾讯软件中心的公开内容接口作为数据源（可再加自定义 JSON 源），但**不含**广告、运营位、捆绑推荐、热搜推广词与遥测上报。

当前版本：**0.10.0**

## 为什么是它

原版联想应用商店便携剪枝后仍有 235 MB / 5 个进程（CEF 浏览器壳），且在线 UI 由服务器下发，运营推广位无法从本地文件彻底移除。MindosShop 直接以合法客户端身份调用内容 API，自己绘制界面：

| | 原版（剪枝后） | MindosShop |
|---|---|---|
| 交付体积 | 234.9 MB | **585 KB（单 exe，静态 CRT）** |
| 进程数 | 5 | **1** |
| 窗口 | CEF 浏览器壳 | **真 HWND** |
| 运行时 | CEF + 124 版 Chromium | **无（仅系统 DLL）** |
| 运营广告位 | 服务端下发，本地管不到 | **从不请求** |

## 技术架构

| 层 | 实现 |
|---|---|
| 窗口 | `CreateWindowExW` + 消息循环，DWM Mica / 沉浸式暗色，最小窗口尺寸约束，per-monitor DPI v2 |
| 渲染 | Direct2D 硬件加速 + **DirectWrite TextLayout 实测排版** + WIC 解码图标；画刷/文本布局/行高缓存、单行省略号裁剪、图标 LRU 预缩放、轴对齐裁剪、设备丢失自动重建 |
| 网络 | WinHTTP（复用系统 TLS 根证书与系统代理），显式处理 HTTP 状态码与重定向；图标下载的 6 线程固定工作池 |
| 数据 | serde_json，仅解析白名单内容接口；多源聚合（联想 / 腾讯 / GitHub / 自定义 JSON）统一映射为同一模型；HTML 简介统一清洗为纯文本 |
| 下载 | 独立任务队列（`downloads.rs`）：流式写盘、实时进度、网络/写盘双路速度、36 秒柱状图 + 趋势折线、暂停/继续、Range 断点续传、任务落盘、3 并发调度 + 自动重试退避、打开所在文件夹 |
| 更新 | 读取卸载项注册表 + **本地**比对商店目录版本（`installed.rs` / `update.rs`），目录快照缓存 + 进入页面/激活窗口时自动重扫描 |
| 并发 | `std::thread` + `PostMessage`，请求带序号以丢弃过期响应 |
| 编译 | LTO + `opt-level="z"` + `panic="abort"` + `strip` + 静态 CRT（无需 VC++ 运行库） |

不打包任何浏览器、.NET、VC++ 运行库或第三方 TLS 栈；只链接 Windows 系统自带 DLL。

## 多源聚合、断点续传与「我的软件」（0.9.0 – 0.10.0）

**更多可靠软件源**：目录不再只来自一家。三个来源统一归一化成同一种应用模型，卡片、更新匹配、下载全链路与来源无关：

| 来源 | 接口 | 特点 |
|---|---|---|
| 联想 | token 内容 API（原有） | 有简介、评分、安装量，也是唯一有详情接口的源 |
| 腾讯 | 公开 JSON `softlistcgi.php` | 免 token，18 个分类各取热门 28 款，直链走 `webcdn.m.qq.com` 并实测支持 `Range` |
| GitHub | Release 页 / REST API（0.10.0 新增） | 开源软件货架，121 款全部实测有 `.exe` / `.msi`，图标取仓库头像，链接在点下载时才解析 |
| 自定义 | 任意 HTTPS JSON 数组 | 内网分发 / 自建目录，字段 `name` `version` `url` `size` `logo` `desc` |

- 合并时按归一化名称去重（保留元数据更全的那条），实测 **联想 + 腾讯 + GitHub = 851 款应用**（联想 341 / 腾讯 395 / GitHub 115，重名的 6 款并入联想行），上一版单源为 246 款
- 横幅内新增来源标签：`全部源 / 联想 / 腾讯 / GitHub / …`，点击即按源过滤（纯内存，不发请求）；进入某个分类时若该分类只有联想数据，筛选自动回到「全部源」而不是空白页
- 单个源超时或格式变更只降级成一条告警，其余源照常出目录；全部源都失败才报错
- 搜索＝联想服务端搜索 + 已加载目录的本地匹配，因此腾讯与自定义源里的软件也能被搜到
- 关闭或新增来源：`%LOCALAPPDATA%\MindosShop\sources.json`

```json
{
  "disabled": ["腾讯"],
  "custom": [{ "name": "我的内网源", "url": "https://example.com/apps.json" }]
}
```

**来源筛选看得见（0.9.1）**：0.9.0 的来源标签只写名字，而且合并后的目录是「联想全量 + 腾讯全量」直接拼接，所以第一屏在「全部源」和「联想」下完全一样，看起来像点了没反应。现在：

- 每个标签自带条数：`全部源 851 / 联想 341 / 腾讯 395 / GitHub 115`，点之前就知道能筛出多少
- 合并时按来源**轮流取样**（联想、腾讯、联想、腾讯…），第一屏立刻是混合结果，与单源视图一眼可分
- 标签占满横幅下半行（统计信息上移成一行），三个来源在最小窗口宽度下也能全部显示
- 从任意分类点回「推荐」直接复用内存里的聚合目录，不再重新请求联想接口——之前返回后目录会缩成联想单源，标签也跟着只剩一个
- 卡片图标缓存从 40 张窗口扩到 400 张并去重，切换筛选 / 分类后不再出现字母占位图

**关闭再打开可以继续下载**：旧版每次启动都从 0 开始，因为任务只存在内存里、`.part` 名字带纳秒时间戳，重启后既找不到任务也找不到文件。

- `.part` 改成 `FNV64(名称 + 下载地址)` 的稳定名，重启后仍能对上同一个任务的残包
- 任务表落盘到 `%LOCALAPPDATA%\MindosShop\downloads.json`；启动时恢复，被上次关机打断的任务恢复为**已暂停**（不会自动重连），点「继续」即从已有字节续传
- 续传使用 `Range: bytes=N-`，并且**每次 302 跳转都重新附带**该头（商店 → 明文 CDN 的跳转会丢掉自定义头）；解析 `206 Partial Content` + `Content-Range` 得到整包大小，进度条从真实百分比开始
- 服务器忽略 Range 返回 `200` 时，检测到「有残包但不是 206」就先截断再从头写，绝不把整包拼在半包后面
- 下载管理新增「暂停」（保留进度）与「继续」；「取消 / 移除」才丢弃残包。残包清理窗口从 6 小时放宽到 7 天，且**在册任务的残包永不删除**
- 实测：预置 300 KB 残包后续传，产物与完整下载**逐字节一致**（1,248,831 字节，PE 头有效）

**下载队列增强**：不再一次点击开一个线程。

- 同时最多 3 个传输，其余进入队列并显示「等待」；任意任务完成或暂停都会立刻把空出的位置交给下一个
- 失败自动重试 2 次（2 秒 / 4 秒退避），每次重试都从 `.part` 续传，不会把已下载的部分重来一遍；用户主动暂停或取消则不再重试
- 「全部更新」改为把整批任务塞进同一队列，享受同样的并发上限、暂停、续传与自动重试

**我的软件（本地库）**：把所有已安装软件列出来，包括商店目录里根本没有的。

- 数据来自卸载项注册表（名称 / 版本 / 发行商 / 主程序 / 卸载命令），本机实测 **160 个已安装、7 个可更新**
- 每行四个动作：`更新`（商店目录有更新版时才出现，走正常下载链路）、`打开`、`定位`（资源管理器选中主程序）、`卸载`
- 卸载先弹**系统模态确认框**，确认后才交给厂商自带的卸载程序（`QuietUninstallString` 优先，其次 `UninstallString`）；本程序自身不删除任何文件、不提权
- 「刷新列表」重新读注册表并同步更新徽标；进入页面时若距上次扫描超过 60 秒也会自动重扫

验证：**72 个单元测试**（新增多源去重、自定义源解析、本地搜索、来源标签几何、软件库按钮几何、续传 `Content-Range` 解析、GitHub 选包规则与清单词表一致性）+ **8 个联网冒烟**；其中「预置残包 → 续传 → 与整包逐字节比对」是真实网络下的端到端用例。真实窗口截图核对：首页（4 个来源标签 / 851 款）、聊天社交分类（56 款 = 联想 36 + 腾讯 15 + GitHub 5）、下载管理（腾讯QQ 换源后 7.2 MB/s、Rufus 从 GitHub 完整下载）、我的软件（160 行、按钮不重叠）。

**分类页也有腾讯源（0.9.2）**：0.9.1 只修好了「推荐」页，点进「聊天社交」这类分类时仍只剩联想——因为分类页是拿中文标签去请求联想接口的，腾讯的分类名与侧边栏不一致（`聊天` vs `聊天社交`、`影音` vs `视频软件`…），对不上自然筛不出来。

- 腾讯的 18 个分类改用**侧边栏完全相同**的词（`聊天社交` `输入法` `浏览器` `下载工具` `视频软件` `音乐软件` `图片图形` `安全防护` `解压刻录` `系统工具` `驱动工具` `办公教育` `编程软件` `理财金融` `剪辑工具` `游戏` `助手工具` `桌面美化`），腾讯条目入库时自带 `category` 字段
- 进入分类页时，除联想服务端结果外，把聚合目录里**同分类的腾讯条目**一并追加再按名称去重；页面标题与来源标签的条数随之变化，不再出现「分类下只有联想」的情况
- 分类名与腾讯分类表完全一致这一点由单元测试锁定（`tencent_categories_match_the_sidebar_vocabulary`），以后改侧边栏会立刻失败提醒

**死链不再让你点了才失败（0.9.2 / 0.9.3）**：腾讯这批直链是 2019 年前后写的静态地址，实测 **243 条已失效**——一部分返回 404，另一部分域名能解析但 CDN 上的对象已被删除。查证结论：**这不是网络问题，也不是地域限制**——`webcdn.m.qq.com` 在境外正常解析，是腾讯自己的列表接口在返回死链，他们网页端点同一个按钮同样 404，客户端根本不走这些 URL。

所以不存在「换个更新的接口就能拿到活链」这条捷径，可行的根本解法只有一条：**不再相信源给的地址，自己把每一行修好**。

- 启动时对聚合目录里**尚未探过**的直链发 `HEAD`（12 个 worker 并发），结果写入 `%LOCALAPPDATA%\MindosShop\urlcheck.json`（24 小时内复用，7 天后清理），第二次启动不再探测
- 判定为死链的行**不再直接删除**：腾讯行拿软件名去其他源搜同款，命中就把 `dl_a` 换成可用链接，名称 / 图标 / 分类 / 简介全部保留；联想行则清掉厂商自己的失效链接，回落到商店按 `softid` 现签的 `dlservice` 地址。两条都是「就地修好」，目录广度一点不损失
- 修好的映射写入 `%LOCALAPPDATA%\MindosShop\mirrors.json`（14 天有效），所以只有**首次启动**要付一次代价（实测探测 7.1 s + 换源 4.3 s，8 并发），之后秒开
- 实测：243 条死链 **243 条修好、0 条被丢弃**；首页从 575 款回到 **736 款**（联想 341 / 腾讯 395），微信、腾讯QQ、TIM 等重新上架且可下载
- 万一仍然漏网（探测通过但下载时已失效），下载失败会自动去其他源搜同名软件换直链重试**一次**；换源后再失败就是终态，不会在源之间来回弹
- 判「链接已死」不只认 HTTP 4xx/5xx：`无法解析域名` / `无法连接` / `超时` / `连接被中断` 同样算死链——腾讯那批老对象里 DNS 失败与对象删除混在一起，只按状态码判断会漏掉一大半
- 失败行的文案改成能看懂的短句：`下载地址已失效（HTTP 404）` / `下载被拒绝（HTTP 403），该地址可能需要登录或限制地区` / `下载服务器暂时不可用（HTTP 5xx）`，不再把 CDN 返回的 `{"errorcode":-46628,…}` 原样贴进列表
- `%TEMP%\mindosshop.log` 里可查 `REPAIR probed=/dead=/rehomed=/dropped=`、`HTTP HEAD … status=404` 与 `DL start` / `DL first chunk` 三类行，定位「到底哪一步没走通」

## 开源货架：第四来源（0.10.0）

商店原先只有联想与腾讯两家，两者都是「国内商业软件目录」，开源软件几乎全靠腾讯源里零散收录的几十款。0.10.0 增加了一个独立来源 **GitHub**，把开源软件做成一层真正的货架。

**为什么只加 GitHub，而不是把所有能想到的站都接上**：先在这台机器上把候选站一个个实测了一遍，结论是大多数站在这里根本用不了，接进去只会得到一排点不动的卡片。

| 候选 | 实测结果 | 结论 |
|---|---|---|
| GitHub `api.github.com` / `releases` | 200，资产 206 分段下载正常 | **接入** |
| SourceForge（含 PortableApps 的下载主机） | 目录页 403、`downloads.sourceforge.net` 403 | 不可用 |
| `raw.githubusercontent.com`（Scoop 清单） | TLS 被阻断，`curl` 直接 exit 35 | 不可用 |
| jsDelivr（Scoop 备用镜像） | 可用，但拉 80 个清单要 31 秒，1711 个要十几分钟 | 收益不抵开销 |
| Uptodown / FileHorse | 连不上（000） | 不可用 |
| Softpedia | 403 | 不可用 |
| Codeberg API | 429 | 不可用 |
| Gitee API | 需要 token，匿名返回空 | 不可用 |
| FossHub | 下载地址由 JS 生成，无稳定直链 | 不可用 |

**目录是编译进 exe 的清单**，`assets/github.json` 里 121 条，每条都实测过最新 Release 里确实有 `.exe` / `.msi`（`tools/github_verified.json` 是验证明细）。清单里**不存链接**——GitHub 的资产地址带版本号，写死就会像腾讯那批一样烂掉。

**链接在点击下载的那一刻才解析**，两条路，都会缓存：

- 先问 REST API `repos/{repo}/releases/latest`：一次往返约 0.8 秒，代价是匿名配额 60 次/小时
- 配额用完或接口异常，回落到 Release 页解析：`/releases/latest` 拿 tag，再取 `expanded_assets/<tag>` 片段里的资产列表，两次请求、不受配额限制
- 结果写进 `%LOCALAPPDATA%\MindosShop\github.json`，24 小时内复用，所以同一个卡片第二次点击是瞬时的
- 解析失败（仓库改行源码发布、只发 ARM 包等）会走既有的跨源换源：用软件名去联想搜索，命中就换链接重试一次

**选包规则**（纯函数 `pick_windows_asset`，单测覆盖）：

| 规则 | 原因 |
|---|---|
| 只接受 `.exe` / `.msi` | 下载完是「安装」按钮，zip/7z/msix 双击没反应 |
| 排除 `.sig` `.sha256` `.asc` `checksums` `.blockmap` | 签名与校验文件常排在资产列表最前 |
| 排除 `arm64` `arm-64` `aarch64` `win-arm` | 装到 x64 机器上直接报错 |
| 排除 `portable` `-cli` `patch` 与 `1061to1064` 这类增量包 | 便携版/命令行版不是用户想要的那个安装程序 |
| 优先 `x64` `amd64` `x86-64` + `setup` / `installer`，并与软件名契合 | 一行里有多个安装包时挑主力构建 |

**分类沿用侧边栏词表**，所以开源软件也会出现在分类页里，不是一个孤立的下拉列表：实测「聊天社交」= 联想 36 + 腾讯 15 + GitHub 5（Telegram Desktop、Mattermost、Rocket.Chat、Zulip、Element）。

**维护清单**：`tools/verify_github.py` 读 `tools/github_candidates.json`（候选：仓库、显示名、分类、一句话简介），逐个解析最新 Release 并打印命中/失败原因，输出 `tools/github_verified.json`；再把通过的那批写进 `assets/github.json` 重新编译即可。新候选加进去跑一遍，几十秒就能知道哪些仓库真的发 Windows 安装包。

实测：GitHub 筛选下 115 款、图标为仓库头像；点 Rufus「获取」→ 日志 `GH pbatard/rufus -> .../rufus-4.15.exe` → 1 秒后开始收字节 → 从 `release-assets.githubusercontent.com` 完整下载 **1,989,992 字节**。

## 一键「安装」下载完成的包（0.8.0）

下载完成后，主操作从「打开位置」改为 **「安装」**：点击即用 `ShellExecuteW("open")` 启动下载到 `Downloads` 的安装包。

- 卡片、详情页、更新页行、下载管理页共用一个任务状态：完成显示「安装」，下载中「取消」，失败「重试」；点击「安装」真正运行安装包，而不是仅在资源管理器里选中文件
- 用 Shell 而非 `CreateProcess` 启动，因此遵循安装包自身清单：`.exe` 请求管理员权限时正常弹出 UAC，`.msi` 交给 `msiexec`，压缩包 / 绿色包走系统关联程序；**程序本身仍不提权、不静默安装**，安装的每一步都交给系统与原安装程序
- 「打开位置」降级为下载管理页的次要按钮，单条「移除」与之并列；缺失 / 被删 / 格式非法的包会给出可操作的中文提示，绝不启动半成品 `.part`
- 安装结束后回到窗口（或切换回来），会本地重扫卸载项并同步更新徽标与「已安装」状态

## 忽略恢复与「已安装」状态（0.7.0）

**忽略过的更新去哪恢复**：之前点「忽略」只是把 `softID` 写进缓存数组，界面上没有任何入口把它们找回来，只能手改 JSON。

- 更新页顶部新增常驻的「已忽略 N」按钮（N=0 也能点，入口始终可发现），点开是独立的忽略列表页，显示软件名、商店版本与「恢复」按钮
- 单项「恢复」或「全部恢复」会立刻用本机注册表做一次**纯本地重匹配**：仍有新版的软件当场回到更新列表，已经升级的则不再出现
- 忽略时把完整条目（名称 / 版本 / 图标 / 下载地址）一并写入 `updates.json` 的 `ignored_items`；旧版只存 ID 的缓存也能从目录快照反查名称，不会出现无法辨认的空条目
- 忽略后的状态栏直接提示「可在『已忽略 N』中恢复」

**本机已装的程序为什么还显示下载**：商店页此前完全不读本机清单，所有卡片一律显示「获取」。

- 启动时只做一次卸载项注册表扫描，构建带归一化名称与已验证启动路径的本机快照；绘制时零注册表 / 零磁盘 I/O
- 名称匹配沿用更新检测的保守规则（归一化后精确或长名包含）；没有 `DisplayVersion` 的国产软件同样纳入，但不会因此误报「有新版本」
- 卡片与详情页显示「已安装 3.9.8 · 已是最新」或「已安装 3.9.8 · 有新版本」；详情页「应用信息」新增「本机状态」行
- 按钮按状态变化：`获取` → `打开`（能定位到主程序时直接启动）/ `已安装`（找不到主程序）/ `更新`（有新版本时下载新版）；已安装应用另保留「重新下载安装包」入口，用于修复或留档
- 启动路径只取 `DisplayIcon` / `InstallLocation` 中真实存在的 `.exe`，处理引号、`,0` 图标索引、环境变量与尾随参数，绝不执行任意命令行；`InstallLocation` 仅在目录里只有一个非安装器 exe 时才采用
- 窗口激活时（2 秒节流）重新扫描，装完或卸载软件后卡片状态与更新数量一起刷新

验证：44 个单元测试（含忽略恢复、旧缓存兼容、已安装判定、安装错误码、四组几何不重叠回归）+ 5 个联网冒烟，`cargo fmt --check` 与 `cargo clippy --all-targets -- -D warnings` 均通过。

## 搜索框、更新状态与实时速度图（0.6.0）

**搜索框**：0.5.0 里点击输入框只是把边框变蓝——没有 I 形光标、没有真正的插入符，placeholder 与「光标」同时显示（光标还被画在 placeholder 末尾），字符只能一律追加到末尾。

- `WM_SETCURSOR` 在输入框区域切换到 `IDC_IBEAM`，离开则恢复箭头
- 500 ms 窗口计时器驱动**闪烁插入符**；聚焦且为空时隐藏 placeholder，光标停在左边缘
- 点击位置按 DirectWrite 实测宽度换算成 UTF-16 插入点；支持 ←/→/Home/End、Backspace/Delete、Ctrl+A 全选、Ctrl+V 粘贴；代理对（emoji）不拆半，中文 IME 逐码元提交也正确
- 输入框命中区从「整个顶部条」收窄为真实矩形，不再点到标题就聚焦

**更新状态**：装完新版本后仍显示「8 个可更新」，是因为列表只在整轮网络检查时刷新，缓存里的旧版本会一直留着。

- 检查结果现在会把**商店目录快照**缓存到 `updates.json`，本机软件清单依旧不上传
- 启动时、进入「软件更新」页、窗口重新激活、下载完成时，用快照 + 卸载项注册表做一次**纯本地重匹配**（无网络请求），已升级的软件立即从列表消失
- 「检查更新」仍会拉最新目录；缓存超过 6 小时进入页面时自动后台刷新

**下载管理 · 实时传输**：类 Steam 的整体速度面板，位于任务列表上方。

- 每 500 ms 采样一次，保留最近 **36 秒 / 72 个样本**；数据来自真实的网络接收字节与 `write_all` 成功写盘字节，各自独立平滑
- **柱状图**：蓝色网络、青色写盘的瞬时速度（半透明）；**折线图**：同一组数据的三点加权平滑趋势，磁盘变慢时会明显落后于网络曲线
- 纵轴按二进制档位（64 KiB → 128 KiB → …）自动缩放，顶部显示当前刻度、峰值、累计传输量
- 任务行与状态栏同步显示「网络 x/s · 写盘 y/s」；无传输时图表面板显示引导文案

## 排版、性能与稳定性（0.5.0）

旧版用「字符数 × 估算宽度」手工折行，而 Direct2D 用真实字体度量排版，两者不一致时多出来的行会直接压到下一个分区标题上，横幅统计、卡片描述、进度百分比也会互相挤在一起。0.5.0 改为**测量驱动**的排版：

- 全部文字改走 `IDWriteTextLayout`：宽度、行数、行高由 DirectWrite 实测，单行文本用 `ellipsis trimming` 自动省略，多行文本按实测高度分配空间，不再预估
- 详情页正文、`本次更新`、`应用信息` 三段的 Y 坐标来自同一份布局测量，绘制与滚动上限使用同一组数值，彻底消除「标题压正文」
- 卡片、横幅、导航、状态栏的分区改为互不重叠的几何带，并有单元测试断言（窄窗口、最大化、拉伸列数三种情况）
- 修复共享 `IDWriteTextFormat` 被 `center_text` 改写对齐方式导致后续标签错位；HTML 简介清洗后按真实行高排布

性能与稳定性：

- 文本布局按「内容 + 宽度 + 字号 + 字重 + 行数」缓存（上限 1024，命中即复用），行高与画刷同样缓存；每帧不再重复创建 DrawText 资源
- 画刷改为借用而非每次 `Clone()`（减少 COM AddRef/Release）；图标改为 160 项 LRU，滚动不再一次性丢弃全部位图重新下载
- 图标请求从「一次 28 个线程」改为 6 线程固定工作池 + 队列，避免 WinHTTP 拥塞拖慢首屏
- per-monitor DPI v2 + `WM_DPICHANGED`，窗口跨不同缩放显示器拖动时重新设置 D2D DPI 并清布局缓存，文字不再忽大忽小
- `EndDraw` 失败时自动重建渲染目标（驱动重置 / RDP 重连 / 休眠恢复后窗口不再全黑）；`GetMessageW == -1` 不再空转占满一个核心
- `.part` 临时文件移入 `%TEMP%\MindosShop` 并在启动时清理超过 6 小时的残包，不再污染 `Downloads`；跨卷保存自动回退为复制
- 32 个测试（27 单元 + 5 联网冒烟），`cargo clippy -- -D warnings` 与 `cargo fmt --check` 均通过

真实窗口验证：1100×720 与最大化 2560×1528（125% DPI）下，分别截取首页 / 详情 / 软件更新 / 下载管理 / 下载中五个界面，文字无重叠、遮挡或截断。

## 下载中心（0.4.0 新增）

此前进度每 **8 MB** 才往状态栏写一行文字，1–3 MB 的安装包一次都不会触发，看起来「点了没反应」。现在下载是一个有完整状态的任务：

- `Content-Length` 在**响应头到达时、第一个数据块之前**就回传给 UI，进度条从 0% 起就有分母
- 每个数据块进入节流进度器（每 1% 或 80 ms 更新一次），显示**百分比 / 已下载 / 总量 / 实时速度**
- 卡片按钮、详情页按钮、底部状态栏、左侧徽标读同一份任务状态：下载中显示进度条与「取消」，完成显示「安装」（点击运行安装包），失败显示「重试」
- 左侧「下载管理」页列出全部任务，支持**取消 / 重试 / 打开所在文件夹 / 移除 / 清空已完成**；状态栏进度区可一键跳转
- 「全部更新」串行排队，未轮到的任务显示「等待下载」，不会九条进度条同时乱跳

实测：`Content-Length = 1,136,096` 在首个数据块前送达，全程 221 个块；1.1 MB 的小安装包产生 100+ 次进度更新（旧版为 0 次）。

## 下载完整性（0.3.0 修复）

商店的 `/dlservice/download?softid=...` 会返回 **302 跳转到明文 HTTP 的 CDN**。WinHTTP 默认禁止 HTTPS→HTTP 降级，旧版既不检查状态码也不读 `Location`，于是读到 0 字节并报「下载内容为空」；软件更新页的「全部更新」同样全军覆没。

现在 `net.rs` 显式接管重定向（最多 6 跳，支持相对路径与协议降级），并做完整校验：

- 非 2xx 直接报错并显示状态码，不再把 404/500 错误页存成 `.exe`
- 重定向后的请求**不携带 token 等身份头**，避免泄漏给第三方 CDN
- 用 `Content-Length` 核对实际写入字节数，读数据出错立即失败而不是当作完成
- 先写 `.part` 临时文件，校验通过才重命名；失败自动删除残包
- 按最终 CDN 文件名选择真实扩展名（`.exe` / `.msi` / `.zip` / `.7z` / `.apk`）
- 校验文件头（PE 的 `MZ`、MSI 的 OLE 头、ZIP 的 `PK`），拦截网关劫持页
- 同名文件自动加序号，不覆盖已有下载

## 纯净策略

**只请求这些接口**（`src/net.rs` 白名单）：

- `/appbase/token/register` — 注册客户端 token
- `/appstorecontents/class/all_classes_list` — 分类树
- `/appstorecontents/class/class_apps_list` — 分类应用列表
- `/searchcontent/search/v4.0/search_apps` — 搜索
- `/appstorecontents/app/details_new` — 应用详情
- 应用图标 CDN、安装包下载直链
- `https://s.pcmgr.qq.com/tapi/web/softlistcgi.php` — 腾讯软件中心公开榜单（可选源，可在 `sources.json` 关闭）
- 用户自行填写的自定义源 URL（默认没有）

**从不请求**：开屏广告、首页运营横幅、`op_recommend_contents`、`system/parameter`（捆绑推荐总闸）、`search_box`（付费热搜词）、`guess/likes`、AI 打点 `pc-fe-ai.lenovomm.cn`、遥测信标 `fsr.lenovomm.com`。搜索结果中 `isAdvert: true` 的条目在解析层直接丢弃。更新检查复用上面的分类/列表接口，不新增任何接口。

## 身份与隐私

程序启动时以最小合法客户端画像（`ch` 版本 + OS 版本）向 `/appbase/token/register` 注册一个临时 token。**不采集、不上传**序列号、UUID、MAC、机型等任何设备标识，也不读取本机原版商店的缓存。

**腾讯源与自定义源只发送列表请求**：`s.pcmgr.qq.com` 的公开列表接口不带任何标识；自定义源的 URL 由用户自己填写。来源可在 `sources.json` 中关闭。

**软件更新是纯本地比对**：程序读取本机卸载项注册表得到「名称 + 版本」，再从商店目录取回「名称 + 版本」，两者只在本机内存中匹配；**本机装了什么软件从不发送给服务器**。检查结果缓存于 `%LOCALAPPDATA%\MindosShop\updates.json`，可随时删除。本机实测扫描到 152 个已安装应用并匹配出 8–9 个可更新项。

本地诊断日志写在 `%TEMP%\mindosshop.log`，超过 1 MB 自动轮转；**不记录响应体或搜索关键词**。

## 功能

- 应用列表、软件分类导航、关键词搜索（支持中文 IME）
- 应用卡片：官方图标、名称、简介、评分、大小、安装量
- 详情页：大图标、完整简介、本次更新、版本 / 大小 / 安装量 / 开发者、可滚动正文
- **下载中心**：实时进度条 / 百分比 / 速度、取消、重试、打开所在文件夹、清空记录
- 下载安装：WinHTTP 流式写盘到 `Downloads`，临时包与签名校验
- **软件更新**：左侧「软件更新」页，支持检查更新 / 单个更新 / 全部更新 / 忽略；版本号分段比较（忽略构建标记误报）、同名取最新版本、中英文名称归一化匹配、结果缓存；安装完新版本自动从待更新列表移除

- **多源聚合**：联想 / 腾讯 / 自定义 JSON 源合并去重，横幅来源标签一键筛选
- **断点续传**：暂停 / 继续、重启后从残包继续、失败自动重试（2 次退避）
- **我的软件**：列出全部已安装软件，支持打开 / 定位 / 卸载 / 一键更新
- 深色/浅色跟随系统、per-monitor DPI v2、滚轮滚动、悬停高亮

> 下载完成后由用户主动点「安装」才会启动安装包（等同于在资源管理器双击该文件）：程序不提权、不静默安装、不在后台自动运行任何安装程序，UAC 与安装向导完全交给系统与原安装包；也可在下载管理点「打开位置」自行处理。更新覆盖度取决于商店目录能否拉到对应软件，名称匹配为启发式，极端命名可能漏报。

## 构建

```powershell
# 需要 Rust（MSVC 工具链，edition 2024 需 >= 1.85）与 Windows SDK
cargo build --release
# 产物：target\release\mindosshop.exe

cargo test                           # 55 个单元测试（布局几何、文本测量、搜索光标、速度采样、更新重扫描、多源聚合、解析回归）
cargo test -- --ignored --nocapture  # 8 个联网冒烟测试（302 / 真实下载 / 进度头 / 断点续传 / 腾讯源 / 多源合并 / 更新匹配）
cargo clippy --all-targets           # 零警告
cargo fmt --check
```

联网冒烟测试默认忽略，其中「真实下载」会向 `Downloads` 写入约 1 MB 的自检安装包，校验通过后自动删除。

GitHub Actions 会在 `windows-latest` 上构建并上传 `mindosshop-windows-x64` artifact；打 `v*` tag 时自动创建 Release。

## 安装

解压发布包后双击 `Install.cmd`（或直接运行 `mindosshop.exe` 免安装使用）。安装为**用户级、无需管理员**：

```
%LOCALAPPDATA%\MindosShop\mindosshop.exe
```

同时创建开始菜单快捷方式与「添加或删除程序」卸载项。程序不写注册表配置、不驻留服务、不设开机自启；仅把更新检查缓存写入 `%LOCALAPPDATA%\MindosShop\updates.json`。exe 未签名，首次运行若被 SmartScreen 拦截，点「更多信息 → 仍要运行」。
